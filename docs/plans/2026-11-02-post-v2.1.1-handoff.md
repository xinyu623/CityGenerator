# Post-v2.1.1 handoff — what is next

Status: `v2.1.1` tagged at `967d3e6 chore: release v2.1.1` and pushed; `main`
carries the unreleased height-sampling v3, patches/viewer, build-stage, CI, and
polish work below. Tests: **233 passed, 3 skipped** (network smoke tests);
`ruff check app tests` clean.
This note is the entry point for the next session: read it first, then pick a
task from the list below.

The older `2026-11-02-v2.1-handoff.md` is the historical plan for the v2.1
feature set; everything in it is released. This note covers what remains.

## What shipped in v2.1

- P2-1 adaptive Overpass splits (four quarters, depth 2, 0.25 km² floor;
  per-cell cache; `source.overpass_splits` / `source.overpass_cell_times`).
- P3-4 stage timings and ~2× faster fusion (`stats["timings_s"]`,
  `metadata.json → timings_s`).
- P1-2 `patches.json` with contiguous ground/wall/bottom ranges in STL order.
- Area-weighted height sampling (0.25–4× footprint area) and, in v2.1.1,
  plausibility guards: clamped heights excluded from the pool; low-rise, civic,
  and industrial types get a sampled ceiling
  (`metadata.buildings.height_sampling.type_capped`).
- CI (`.github/workflows/ci.yml`) and the 300 m golden city
  (`tests/golden/city_300m.json`, refresh with `UPDATE_GOLDEN=1`).
- CLI GBK-console fix.

## Next tasks, in priority order

### 1. Height sampling v3 (P1) — DONE, unreleased

Implemented on `main` (see `docs/plans/2026-11-02-height-sampling-v3.md` for the
plan and the decisions): the sampler now draws from observations within
`0.5–2×` the target footprint area, weighted by a log-area kernel
(`AREA_BANDWIDTH_LOG = 0.5`) and by `building` type (same type ×2, same type
group ×1.5), instead of a uniform draw inside the old `0.25–4×` band. The hard
band stayed because the kernel alone still let a 112 m² building copy a 239 m
tower (the candidates just get unlikely, not impossible). Each sampled building
records `height_rule` (`similarity`, `type_cap`, `conservative_cap`) in
`buildings.geojson`; `metadata.buildings.height_sampling` gained the pool's and
the sample's ≥100/≥250 m counts by type group, rule counts, `sampled` (prepared
polygon parts) vs `sampled_buildings` (distinct OSM buildings) and
`band_fallback_draws`, `area_ratio` (`[0.5, 2.0]`), `area_bandwidth_log`, and
`type_factors`. Optional conservative
mode: `--conservative-heights` / `--no-conservative-heights` /
`CITYGEN_HEIGHT_SAMPLING_CONSERVATIVE`, bound `height ≤ k·√area`, `k = 8`.
Validation script: `python -m app.services.height_report --output <job> [--check]`.

4×4 km result against the v2.1.1 baseline: sampled ≥250 m 21 → 17 (pool 2.6 %),
≥100 m 73 → 69 (pool 8.9 %), samples with height/√area > 10 12 → 1, worst ratio
17.0 → 10.9; conservative mode: 15 above 250 m and no sample above ratio 8.
Triangles 84 382 → 87 388, volume 1.33981e9 → 1.33733e9 m³, still watertight
with 0 weld repairs and 0 non-manifold edges.

Not addressed: the pool's 3 m mode (356 buildings tagged `building:levels=1`)
still makes 1 218 of 1 697 buildings 3.5 m or lower. That is the tagged pool's
own shape, not a sampling bug; changing it is a product decision (task 5).

The original brief, kept for the record:

- Stratify the pool by `building` type: same type first (if at least ~5
  observations), then a type group (residential / commercial / civic /
  industrial / other), then the 0.25–4× area band, then all observations; or
  weight candidates by type + log-area similarity instead of hard bands.
- Add an optional conservative mode (for example height ≤ k·√area or a
  percentile cap) for users who want a calmer skyline, and record which rule
  produced each sampled height.
- Record outlier statistics in `metadata.buildings.height_sampling` (sampled
  above 100/250 m, by type, stratum used) and add a 4×4 validation script.
- Acceptance: no sampled low-rise/civic type exceeds its ceiling; the ≥250 m
  sampled share does not exceed the tagged pool's share; deterministic tests
  for stratification and the conservative bound; 4×4 rerun report + visual
  check; docs and CHANGELOG updated.

### 2. patches.json on steep terrain + viewer colours (P1) — DONE, unreleased

`ground` used to be "upward normal and centroid within
`CITYGEN_PATCH_GROUND_TOLERANCE_M` = 0.05 m of the TIN", so a near-surface roof
triangle on a steep slope could be mislabelled, and the Three.js preview used
one material.

Implemented: `face_kinds` now requires the centroid **and all three vertices**
within the tolerance and the face normal to agree with the terrain normal
(`CITYGEN_PATCH_GROUND_NORMAL_DOT_MIN` = 0.9; flat runs compare with the `z = 0`
plane). `TerrainGrid.surface_normal` mirrors `surface_z`'s TIN split. On the
4×4 km sample 97 of 54 615 old `ground` faces were wrong (73 near-surface
roof/wall triangles with a vertex up to 0.34 m off the surface, 24 near-vertical
slivers with |nz| ≈ 0.02); ground 54 615 → 54 518, wall 32 225 → 32 322, bottom
548, ranges 950 → 774, geometry unchanged (87 388 triangles, same volume). The
1 km² box (29.560551,106.581970 → 29.569449,106.592431) has 3 721 ground faces,
every vertex within 0.08 mm of the surface, normal dot ≥ 0.996.

The preview loads `city.stl` + `patches.json`, splits the non-indexed geometry by
the recorded ranges into `ground` / `wall` / `bottom` meshes with their own
materials, lists the counts in the footer legend, and falls back to
`preview.stl` with one material when `patches.json` is missing or unreadable;
when the ranges do not cover the mesh it keeps `city.stl` in one material and
warns in the console. The result panel shows a `地面 / 墙面` card
(`stats.patch_counts`, `stats.patch_ranges`). `patches.json` and the metadata
`patches` block record `ground_normal_dot_min`. Tests cover the slope/roof,
vertical-sliver, steep-TIN and 45° terrain cases; `README` images were
regenerated.

### 3. build-stage performance (P2) — DONE, unreleased

`extrude_prepared` was dominated by per-shell `trimesh` bookkeeping, not by the
extrusion: each of the ~1 700 shells was copied, went through the generic
`update_faces`/`fix_winding`/`fix_normals` chain even when it was already
closed, and then `_mesh_is_valid` re-derived watertightness, winding, and volume
from cached properties. The shell is now built with shared ring vertices
(`_extrude_polygon`, used by `extrude_building`) and measured in one sorted-edge
pass (`_shell_report`: closure, winding, volume, degenerate faces, finite
coordinates); the legacy repair chain runs only for a shell that report cannot
accept. The triangle sets are identical to
`trimesh.creation.extrude_polygon` (`test_extruded_shell_matches_trimesh_polygon_construction`).
`_contact_indices` is one `STRtree.query(..., predicate="dwithin")` instead of
one buffered query per footprint, and `TerrainGrid.min_over` samples the rings
and the representative point in one `surface_z` call.

The city STL is exported once. `fuse_city` keeps the bytes it already
round-tripped to prove closure and the mesh read back from them
(`FusedCity.stl_bytes`/`stl_mesh`) and validates that file; `write_outputs`
writes and classifies those bytes instead of exporting, reloading, and
validating a second time. The pipeline also passes `check_input_volumes=False`
to the boolean engine: each shell was validated already, and the fused mesh and
the written file still are.

Interleaved before/after on the cached 4×4 km sample (ABBA order, two runs per
side; the machine throttles under load, so min/median are both shown):

| stage | before (s) | after (s) | speedup |
| --- | --- | --- | --- |
| build | 2.03 / 2.06 | 0.89 / 0.98 | 2.1× |
| fuse | 0.81 / 0.82 | 0.81 / 0.84 | ≈1.0× |
| export | 0.63 / 0.66 | 0.34 / 0.38 | 1.8× |
| total | 5.77 / 5.83 | 4.29 / 4.50 | 1.34× |

`fuse` is at parity: it now owns the reloaded-file validation that used to run
in `export`, and the two stages together fall from 1.43 s to 1.14 s. The
acceptance run is byte-identical to
`artifacts/height-sampling-v3/output/city.stl`: 87 388 triangles, volume
1.33733e9 m³, watertight, 0 non-manifold edges, 0 weld repairs, patches
54 518 / 32 322 / 548 in 774 ranges. Fetch and the ZIP write are unchanged.

### 4. CI hardening (P2) — DONE, unreleased

`.github/workflows/ci.yml` now has two jobs, each with `timeout-minutes`: the
Ubuntu one (20 min) and `test-windows` on `windows-latest` (30 min). Both
install `.[dev]`, run `ruff check app tests`, and run the offline suite; the pip
cache comes from `actions/setup-python`'s `cache: pip`.

Instead of exact pins, `tests/golden/city_300m.json` records the producer
versions (`python`, `trimesh`, `manifold3d`, `pyproj`, `shapely`, `numpy`) next
to the metrics, and `test_golden.py` appends both version sets and the changed
names to any metric mismatch. A version-only change still passes: the record
only makes a future failure explain itself. `UPDATE_GOLDEN=1` refreshes the
metrics and the producer block together. The golden test stays in the main
suite (it takes a couple of seconds) rather than a separate job that would pay
for another install.

### 5. Product polish / data hygiene (P3) — DONE, unreleased

- UI area: `map.js` computes the WGS84 cell area in closed form
  (`A = Δλ·a²(1−e²)·[F(sin φN) − F(sin φS)]`) instead of planar
  `width × height`; a 4×4 km selection reads 16.005 km², the value the backend
  validates. `tests/test_frontend_area.py` runs the shipped module under Node
  and compares five boxes against `bbox_area_km2` (skipped when `node` is
  missing).
- `metadata → buildings.height_sampling` has one shape in every mode:
  `enabled`, `reason`, zero counters, empty maps, and the configured parameters.
  The height report prints `disabled (<reason>)` instead of leaving the block
  unexplained.
- Huge low-rise footprints: **kept**. They are real OSM shapes; the documented
  control (`min_building_area_m2`) only drops small buildings, and a new
  max-area filter would delete real city fabric. Recorded in
  `docs/osm-to-stl.md` §10.
- Optional OBJ with ground/wall groups: **not added**. It would grow every job
  and ZIP (the fused STL is already ~4.4 MB) while `patches.json` carries the
  same grouping in STL order; a future opt-in `--obj` flag is the escape hatch.

### Found on the way, not fixed

The height sampler can draw a height below the building's own tagged base: two
of the 1 699 prepared items have a sampled height of 3.1/3.2 m on an 18 m
`min_height`, so `extrude_building` raises `height must be greater than base`
and `extrude_prepared` skips them under the `TRIANGULATION_FAILED` warning
(whose message is then misleading). The 1 696 buildings and every reference
number include that existing skip. Clamping a sampled height to `base + 0.5`
would fix it but changes the reference geometry, so it is a separate change.
