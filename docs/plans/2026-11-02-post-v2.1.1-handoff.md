## Next tasks, in priority order

### 1. Height sampling v3 (P1) — DONE, unreleased

Implemented on `main` (see `docs/plans/2026-11-02-height-sampling-v3.md` for the
plan and the decisions): the sampler now draws from observations within
`0.5–2×` the target footprint area, weighted by a log-area kernel
(`AREA_BANDWIDTH_LOG = 0.5`) and by `building` type (same type ×2, same type
group ×1.5), instead of a uniform draw inside the old `0.25–4×` band. The hard
band stayed because the kernel alone still let a 112 m² building copy a 239 m
tower (the candidates just get unlikely, not impossible). Each sampled building
records `height_rule` (`similarity`, `type_cap`, `conservative_cap`) in
`buildings.geojson`; `metadata.buildings.height_sampling` gained the pool's and
the sample's ≥100/≥250 m counts by type group, rule counts, `area_ratio`
(`[0.5, 2.0]`), `area_bandwidth_log`, and `type_factors`. Optional conservative
mode: `--conservative-heights` / `CITYGEN_HEIGHT_SAMPLING_CONSERVATIVE`, bound
`height ≤ k·√area`, `k = 8`. Validation script:
`python -m app.services.height_report --output <job> [--check]`.

4×4 km result against the v2.1.1 baseline: sampled ≥250 m 21 → 17 (pool 2.6 %),
≥100 m 73 → 69 (pool 8.9 %), samples with height/√area > 10 12 → 1, worst ratio
17.0 → 10.9; conservative mode: 15 above 250 m and no sample above ratio 8.
Triangles 84 382 → 87 388, volume 1.33981e9 → 1.33727e9 m³, still watertight
with 0 weld repairs and 0 non-manifold edges.

Not addressed: the pool's 3 m mode (356 buildings tagged `building:levels=1`)
still makes 1 218 of 1 697 buildings 3.5 m or lower. That is the tagged pool's
own shape, not a sampling bug; changing it is a product decision (task 5).

The original brief, kept for the record:

- Stratify the pool by `building` type: same type first (if at least ~5
  observations), then a type group (residential / commercial / civic /
  industrial / other), then the 0.25–4× area band, then all observations; or
  weight candidates by type + log-area similarity instead of hard bands.
- Add an optional conservative mode (for example height ≤ k·√area or a
  percentile cap) for users who want a calmer skyline, and record which rule
  produced each sampled height.
- Record outlier statistics in `metadata.buildings.height_sampling` (sampled
  above 100/250 m, by type, stratum used) and add a 4×4 validation script.
- Acceptance: no sampled low-rise/civic type exceeds its ceiling; the ≥250 m
  sampled share does not exceed the tagged pool's share; deterministic tests
  for stratification and the conservative bound; 4×4 rerun report + visual
  check; docs and CHANGELOG updated.

### 2. patches.json on steep terrain + viewer colours (P1)

`ground` is currently "upward normal and centroid within
`CITYGEN_PATCH_GROUND_TOLERANCE_M` = 0.05 m of the TIN". On steep terrain a
near-surface roof triangle can be mislabelled `ground` (documented risk).
Separately, the Three.js preview uses one material, so `patches.json` is
invisible in the UI.

- Require the face normal to agree with the terrain normal (dot ≥ ~0.9), or
  compare the whole triangle plane to the terrain instead of only the centroid;
  add a synthetic slope + low building regression test; quantify how many
  `ground` faces are roofs on the 4×4 sample.
- Colour ground/wall in the preview from `patches.json` (fetch via the job file
  URL) and show the patch counts in the result stats.
- Acceptance: ranges still cover 100 % without overlap; hand check on a 1 km²
  sample; UI shows the two patch colours; docs updated.

### 3. build-stage performance (P2)

The cached 4×4 run is ~14 s under throttle (~8–9 s idle): `build` (contact
buffer, terrain `min_over`, triangulation, per-shell validation) is ~8–10 s,
`fuse` ~2.4 s, `export` ~1.2–1.8 s. `extrude_prepared` is the next lever.

- Profile `extrude_prepared` step by step (`min_over`, per-shell
  `is_watertight`/`fix_winding`, triangulation, contact buffers) and optimise
  the dominant step.
- Remove the duplicate STL round-trip: `fuse_city` exports and reloads the city
  to check closure, then `write_outputs` exports, reloads and validates again.
  Reuse the validated bytes/mesh.
- Acceptance: watertight, 0 non-manifold edges, volume within 1e-4, triangle
  count unchanged or explained; interleaved before/after timing table.

### 4. CI hardening (P2)

- Add a Windows job: the GBK console bug was Windows-only, and the docs are
  PowerShell-first. Add `timeout-minutes` to both jobs.
- Pin `trimesh`, `manifold3d`, `pyproj`/`shapely` versions, or record the
  producer versions inside `tests/golden/city_300m.json`, so a dependency bump
  cannot fail CI on an unchanged commit without explaining itself.
- Optional: cache the pip download, keep the golden test in its own job.

### 5. Product polish / data hygiene (P3)

- UI area formula: the front end uses planar `width × height`, the backend the
  ellipsoid (4×4 km = 16.000 vs 16.005 km²); unify when touching the frontend.
- Optional OBJ with ground/wall groups for Blender/Salome (the optional item
  from the v2.1 P1-2 task).
- Decide whether to filter huge low-rise plaza/market footprints (e.g.
  21 964 m² at 3 m, 68 000 m² at 23 m). They are real OSM shapes; removing them
  is a product decision, not a bug fix.
- Make `metadata.buildings.height_sampling` shape stable: `area_weighted`,
  `area_ratio`, `type_capped` exist only when sampling ran.
